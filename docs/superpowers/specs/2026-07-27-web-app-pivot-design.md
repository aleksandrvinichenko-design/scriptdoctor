# Script-Doctor AI — смена концепции на веб-приложение (черновик, брейнсторм в процессе)

**Статус: НЕ завершено.** Это не финальный согласованный дизайн, а слепок решений, принятых в
брейнсторм-сессии 2026-07-27, чтобы не потерять контекст при переходе в другую сессию. Продолжать
брейнсторм с того места, где он остановился (см. «Открытые вопросы» внизу), по скиллу
`superpowers:brainstorming` — не пропускать сразу к реализации.

## Зачем этот документ

Пользователь решил полностью сменить концепцию проекта. Старая концепция (см. `CLAUDE.md`,
`core/`, `.claude/skills/` в этом репозитории) — аналитический инструмент внутри Claude Code,
работающий через markdown-скиллы, с явным спором нескольких теоретических школ и сохранением
развилок между ними. Новая концепция — совсем другой продукт с другой философией. Ниже — то, что
уже решено, и то, что ещё нет.

## Новое видение продукта

Полноценное веб-приложение для написания киносценариев в формате «американка» (как WriteDuet /
Kit Сценарист), с ИИ-ассистентом, встроенным в процесс написания на каждом этапе — от логлайна до
реплик в сценах. В отличие от старой концепции, ассистент не показывает пользователю спор разных
теоретических голосов — он работает как единый синтезированный помощник и может не только
анализировать, но и предлагать черновые варианты текста.

## Решено (зафиксировано в диалоге)

1. **Формат продукта** — настоящее веб-приложение со своим UI, не чат внутри Claude Code.
2. **Редактор** — строить на базе **Fountain** (открытый текстовый стандарт разметки сценариев) и
   существующих открытых JS-парсеров/рендереров под него (например, экосистема `fountain-js` /
   Afterwriting), а не писать логику форматирования американки с нуля. Референс на архитектуру
   (не код — там C++/Qt) — открытый преемник Kit Сценарист.
3. **Порядок разработки** — начинаем с ИИ-ассистента (не с редактора), несмотря на то что редактор
   технически более базовый слой. Явный выбор пользователя.
4. **ИИ-инфраструктура** — свой хостинг, компания платит за API (Anthropic/OpenAI), пользователь
   ничего не настраивает сам. Это требует полноценного бэкенда (авторизация, хранение проектов,
   в перспективе — биллинг/подписка; вопрос монетизации отложен, не проектировался).
   Полностью локальная дообученная модель — рассмотрена и отклонена для v1: качество заметно ниже
   Claude, требует огромного (и юридически рискованного) корпуса сценариев для обучения и мощностей
   на тренировку. Может вернуться как облегчённый офлайн-режим в будущем, не как требование к v1.
5. **Никакого разделения на школы.** Это прямой разворот главного принципа старой концепции.
   Все книги (сейчас 6 модулей: howard, snyder, kaplan, weiland, field, truby) синтезируются в
   один голос. Ассистент сам ведёт проект в направлении того, чему он «более всего соответствует»
   по контексту — не показывает развилки, не называет школы пользователю.
6. **Ассистент может генерировать текст**, а не только анализировать — черновики реплик, описаний
   сцен и т.д., которые автор правит или отклоняет. Это тоже разворот старого принципа
   («Script-Doctor AI — не генеративный инструмент») — в новой концепции генерация разрешена.
7. **Референсные фильмы** — пользователь в начале проекта выбирает несколько уже снятых
   фильмов/сериалов как референс. Технически это расширение уже существующей идеи `/script-learn`:
   разбираем реальный сценарий, **не храним авторский текст**, храним только структурированную
   аналитическую выжимку (функция бита, дуга персонажа, тема и т.д. — по аналогии с
   `training/screenplays/*.md` в старой концепции, но без деления по школам).
8. **UX ассистента** — боковая панель-чат рядом с редактором (как Cursor/Copilot Chat), не встроенные
   построчные комментарии и не отдельный полноэкранный режим.
9. **Стратегия контекста проекта (Вариант C, выбран, но не финализирован до конца)** — гибрид:
   - всегда в контексте — дешёвая автообновляемая «сводка проекта» (логлайн, тема, дуги персонажей,
     где сейчас находится сюжет) + текст текущей сцены целиком;
   - остальное (прошлые сцены, референсы) подтягивается по явному запросу или простому совпадению
     (жанр/персонаж/ключевые слова), без векторной базы/эмбеддингов на старте;
   - естественный путь апгрейда до полноценного RAG (Вариант B) позже, если понадобится.
   - Валидировано внешним примером: Sudowrite (закрытый коммерческий сервис, не open source,
     надстройка над чужими LLM) использует концептуально то же самое — механизм «Story Bible»:
     постоянная структурированная сводка истории, подмешиваемая в каждый запрос к ИИ, плюс набор
     точечных инструментов (Write/Describe/Rewrite/Brainstorm/Feedback) поверх неё.

## Что переносится из старого проекта

- Дистиллированное содержимое `training/books/*.md` (6 книг) — ценность сохраняется, но
  интеграция меняется: раньше это были отдельные неслияемые модули с сохранением развилок,
  теперь — сырьё для единой синтезированной базы знаний ассистента.
- Идея двухслойной записи из `/script-learn` (полная интерпретация + нейтральный индекс-лейбл) —
  подходит как основа для обработки референсных фильмов, только без привязки к конкретным школам.
- Общая дисциплина «не хранить/не выдавать сырой копирайтный контент, только дистилляцию» —
  прямо переносится на референсные фильмы в новом продукте.

## Что НЕ переносится / прямо противоречит старой концепции

- Всё в `CLAUDE.md` §1–§2 про запрет усреднения школ и обязательное сохранение развилок —
  отменяется для нового продукта.
- Принцип «не генеративный инструмент» (первая строка `CLAUDE.md`) — отменяется.
- Формат работы через markdown-скиллы в Claude Code — заменяется настоящим бэкендом/фронтендом.

## Открытые вопросы (брейнсторм на этом остановился)

Ничего из списка ниже ещё не решено — продолжать отсюда в следующей сессии:

1. Финализировать Вариант C для контекста: как именно выглядит структура данных «сводки проекта»,
   как она обновляется (после каждой сцены? по явному запросу?), что конкретно значит «простое
   совпадение» при подтягивании прошлых сцен/референсов.
2. Что конкретно делает ассистент на каждой стадии по-разному — логлайн vs тритмент vs сцена/диалог
   (какие вопросы задаёт, что предлагает, в каком объёме генерирует текст).
3. Модель данных проекта и хранения (структура БД, как соотносятся Fountain-документ и
   структурированные метаданные типа персонажей/арок/референсов).
4. Как именно референсные фильмы попадают в систему технически — пользователь сам загружает файл
   сценария, или это делает команда заранее и собирает библиотеку референсов, из которой выбирает
   пользователь?
5. Судьба текущего репозитория — новый репозиторий/кодовая база, или эволюция текущего
   `claude-script-doctor`?
6. Не спроектировано вообще: сам редактор (структура проекта — акты/сцены/карточки, экспорт,
   совместная работа), авторизация, монетизация/биллинг, онбординг нового пользователя.

## Как продолжить

Открыть новую сессию, указать на этот файл, и продолжить брейнсторм с раздела «Открытые вопросы» —
по-прежнему по одному вопросу за раз, без перехода к реализации до финального одобрения дизайна
(см. `superpowers:brainstorming`).
