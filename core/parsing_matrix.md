# Parsing Matrix — модульная схема разбора сценария

Эта схема используется и `/script-learn`, и `/script-doctor` для разбора любого текста (черновик автора
или эталонный сценарий) на единую структуру данных. Правила неусреднения и неразрешения развилок из
[`CLAUDE.md`](../CLAUDE.md) обязательны при заполнении этой схемы.

Схема состоит из трёх слоёв: **Base Layer** (нейтральные координаты), **Beat Layer** (событийная
разметка) и **Module Layer** (произвольное число независимых, ничем не упрощённых модулей — по одному
на каждую книгу, зарегистрированную через `/book-learn`). Base и Beat Layer никогда не содержат
терминологии конкретного модуля — они существуют только для того, чтобы у всех текущих и будущих
модулей была общая точка адресации.

**Этот файл не содержит списка модулей и их полей.** Список того, какие модули сейчас существуют,
живёт как факт файловой системы — это набор файлов в `training/books/*.md`. Схема каждого модуля
(какие у него поля, какие обязательны) хранится внутри соответствующего файла книги, а не здесь
(см. §1 `CLAUDE.md` и `.claude/skills/book-learn.md`).

## Base Layer — структурные координаты

Присваивается каждому анализируемому фрагменту. Это адрес, а не интерпретация.

```yaml
coordinate:
  act: <int>                # 1 / 2A / 2B / 3 — либо иная принятая для жанра структура
  scene_range: <str>        # напр. "34-37" — номера сцен или диапазон страниц
  characters_present: [str] # действующие лица в этом фрагменте
  pov_character: <str|null> # чья точка зрения ведёт фрагмент, если применимо
```

Base Layer не отвечает на вопрос «что это значит». Он отвечает только на вопрос «где это находится».

## Beat Layer — событийная разметка

Story beat — минимальная драматургическая единица: конкретное сюжетное событие, а не номер страницы.
Один beat может охватывать несколько сцен из Base Layer или их часть.

```yaml
beat:
  beat_id: <slug>            # напр. "ally-betrayal-reveal"
  description: <str>         # одна фраза, нейтральный факт: "герой узнаёт о предательстве союзника"
  coordinate_ref: <coordinate.scene_range>  # привязка к Base Layer
```

`beat_id` — это нейтральный индексирующий лейбл (см. `CLAUDE.md §5`). Он не интерпретирует событие,
не принадлежит ни одному модулю и используется исключительно для поиска и сопоставления жанров при
синтезе Meta-Reference. Все модули Module Layer привязываются к `beat_id`, а не наоборот — это то,
что позволяет debate-движку понять, что несколько вердиктов разных модулей относятся к одному и тому
же моменту истории, даже если эти модули были зарегистрированы в разное время и ничего не знают друг
о друге напрямую.

## Module Layer — контракт модуля

Любая книга, прошедшая через `/book-learn`, становится **модулем**. Модуль — это:

1. Уникальный `module_key` (короткий slug, обычно от фамилии автора или названия книги).
2. Набор полей, каждое из которых отвечает на диагностический вопрос именно этой книги, в её
   собственных терминах — без упрощения и без подгонки под поля других модулей.
3. Для каждого поля — пометка `required: true/false`, которую модуль расставляет сам при регистрации
   (используется гейтами `core/pipeline_config.md`, см. `CLAUDE.md §4`).

Формальных требований к содержанию полей эта схема не накладывает — их определяет книга. Единственное
структурное требование: каждое заполненное значение поля модуля обязано быть привязано к `beat_id`.

```yaml
# Пример формы, которую принимает разбор ОДНОГО beat одним модулем.
# Конкретные имена полей ("ghost", "want", "beat_sheet_slot" и т.п.) здесь — не встроенные требования,
# а лишь иллюстрация того, как может выглядеть модуль, если книга вводит такие понятия.
<module_key>:
  beat_id: <ref>
  <field_name>: <value>   # столько полей, сколько модуль объявил в своей схеме
  ...
```

Когда зарегистрировано ноль модулей — Module Layer пуст, `/script-doctor` сообщает об этом честно и
не имитирует анализ (см. `CLAUDE.md §7`). Когда зарегистрирован один модуль — Theoretical Consensus
Layer работает как единственный голос, без развилок с оппонентами, которых не существует.

## Meta-Reference поля (заполняются только для эталонных сценариев в `training/screenplays/`)

Эти поля добавляются поверх Module Layer при разборе эталонного сценария в рамках `/script-learn`
и используются исключительно для синтеза Meta-Reference (см. `.claude/skills/script-learn.md`).

```yaml
meta_reference:
  beat_id: <ref>
  function_tag: <str>          # драматургическая функция beat для конкретного героя (function-over-form)
  variance_axis: <str>         # к какой оси вариации внутри жанра относится это исполнение
  variance_position: <str>     # инвариант / частая реализация / редкая реализация — где именно на оси
  default_deviation: <str|null> # как это исполнение уклоняется от жанрового дефолта в этой точке (опционально)
```

`function_tag` формулируется в терминах того, что важно для героя (want/need/flaw-эквивалент), опираясь
на модули, реально зарегистрированные на момент разбора — не на предполагаемый универсальный словарь.

## Развилки (Forks)

Когда два и более модуля дают несовместимые диагнозы одного `beat_id`, это фиксируется отдельной
структурой, а не переписыванием одного из полей:

```yaml
fork:
  beat_id: <ref>
  conflicting_modules: [str]   # module_key вовлечённых модулей, любое их число ≥ 2
  positions:
    - module: <str>
      claim: <str>
  resolved_by: <"author"|null> # null пока автор не сделал выбор через интерактивное поле `[ ]`
  resolution: <str|null>
```

Развилка никогда не блокирует прогресс по pipeline (см. `core/pipeline_config.md`) — это чисто
рекомендательная структура. При одном зарегистрированном модуле развилок не бывает по определению.

## Соответствия между терминами модулей

Пересечения терминов между уже добавленными модулями (например, «Need» у одной книги и «Moral Need»
у другой) документируются по мере накопления книг — не заранее — в
[`core/term_correspondence_map.md`](term_correspondence_map.md). Этот файл не является частью данной
схемы и никогда не используется программно для слияния полей.
