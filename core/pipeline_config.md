# Pipeline Config — гейты стадий

Три стадии: **Logline → Character → Treatment**. Переход между ними регулируется правилом A+D из
[`CLAUDE.md §4`](../CLAUDE.md#4-блокировка-стадий--узкая-и-не-зависящая-от-конкретного-набора-модулей):

- **(A) Пустые обязательные поля** — блокирует.
- **(D) Жёсткий, не зависящий от содержания конкретных модулей чек-лист структурного отсутствия** — блокирует.
- Теоретические развилки между модулями (§2 CLAUDE.md) — **никогда не блокируют**.
- Результат Empirical Crash-Test (§3 CLAUDE.md) — **никогда не блокирует**, только советует.

Ни один гейт ниже не называет конкретный модуль или книгу по имени. Набор модулей заранее неизвестен —
гейт обязан оставаться корректным и при нуле зарегистрированных модулей, и при одном, и при десяти.

Если гейт останавливает прогресс по причине, не входящей в списки ниже — это ошибка конфигурации,
а не ожидаемое поведение.

---

## (A) Пустые обязательные поля — общий механизм

Обязательность поля определяется не этим файлом, а самим модулем, в момент его регистрации через
`/book-learn` (поле `required: true` в схеме модуля — см. `.claude/skills/book-learn.md` и
`core/parsing_matrix.md`, раздел Module Layer). Правило одно и то же для всех стадий:

```yaml
rule: "для каждого модуля, зарегистрированного в training/books/, и для каждого его поля,
       помеченного required: true — если это поле применимо на текущей стадии (см. ниже),
       оно должно быть заполнено для релевантного beat_id."
```

«Применимо на текущей стадии» определяется тем, к какому логическому слою относится поле в схеме
модуля (сам модуль указывает это при регистрации: `applies_to: logline | character | treatment`).
Если модуль не указал `applies_to` для поля — считать его применимым только на стадии Character,
как наиболее общей.

Если зарегистрированных модулей нет вообще — проверка (A) по модулям пропускается (нечего проверять),
но базовые универсальные поля Base/Beat Layer (см. ниже, стадия Logline) всё равно обязательны — они
не зависят от модулей.

---

## Стадия 1: Logline

### (A) Обязательные поля (универсальные, не зависят от модулей)

```yaml
required_fields:
  - protagonist.name
  - protagonist.external_goal
  - central_obstacle
  - genre_type
```

Эти поля — часть Base Layer / общей оболочки черновика, а не какого-либо конкретного модуля, поэтому
существуют независимо от того, сколько книг сейчас зарегистрировано.

### (D) Чек-лист структурного отсутствия

```yaml
hard_checks:
  - id: active_protagonist
    fail_if: "протагонист не совершает ни одного действия для достижения цели — только реагирует на события"
  - id: stated_external_goal
    fail_if: "external_goal не сформулирована как конкретный, проверяемый результат"
  - id: obstacle_exists
    fail_if: "central_obstacle отсутствует или тождественен самому протагонисту без внешнего или внутреннего препятствия"
```

Ничего в этой стадии не проверяет качество или глубину логлайна — это территория дебатов на
`/script-doctor`, а не гейта.

## Стадия 2: Character

### (A) Обязательные поля

Берутся динамически: все поля всех зарегистрированных модулей с `required: true` и
`applies_to: character` (или без явного `applies_to`, см. правило выше).

Поле считается пустым, если оно отсутствует или дословно совпадает с полем другого модуля (то есть
было скопировано, а не заполнено самостоятельно — см. запрет на слияние терминов в `CLAUDE.md §1`).

Если на момент проверки зарегистрирован только один модуль (или ни одного) — гейт проверяет только
его (их) обязательные поля; отсутствие «оппонирующих» модулей само по себе не является причиной
блокировки.

### (D) Чек-лист структурного отсутствия (универсальный, не зависит от модулей)

```yaml
hard_checks:
  - id: internal_contradiction_present
    fail_if: "во всех заполненных полях всех модулей нет ни одного намёка на внутренний конфликт персонажа — герой полностью прозрачен и непротиворечив"
  - id: change_potential_present
    fail_if: "ни один зарегистрированный модуль не фиксирует ничего, что могло бы измениться к концу истории"
```

Эти два чек-пункта сформулированы абстрактно специально, чтобы не зависеть от того, какая именно
книга их фактически детектирует — Character-стадия требует минимальной глубины персонажа в принципе,
а не конкретной терминологии конкретного теоретика.

Расхождение модулей в диагнозе (например, два модуля по-разному читают один и тот же момент)
фиксируется как fork в `parsing_matrix.md` и **не является причиной блокировки** — гейт проверяет
только структурное наличие ответа, не согласие модулей по его содержанию.

---

## Стадия 3: Treatment

### (A) Обязательные поля

```yaml
required_fields:
  - beats[]                        # полная последовательность story beat из Beat Layer
  - beats[].coordinate_ref
```

Плюс — динамически: поля всех зарегистрированных модулей с `required: true` и `applies_to: treatment`.

### (D) Чек-лист структурного отсутствия

```yaml
hard_checks:
  - id: no_orphan_beats
    fail_if: "beat из Beat Layer не привязан ни к одной сцене Base Layer"
  - id: no_orphan_scenes
    fail_if: "сцена из Base Layer не привязана ни к одному beat_id"
  - id: full_act_coverage
    fail_if: "хотя бы один заявленный акт истории не содержит ни одного beat"
  - id: midpoint_present
    fail_if: "во всей истории нет ни одного beat в позиции, эквивалентной середине истории"
```

Эти проверки сформулированы на языке Base/Beat Layer — они работают одинаково независимо от того,
какие модули сейчас зарегистрированы, и не сломаются при добавлении или отсутствии конкретной книги.

Все остальные вопросы на этой стадии — глубина проработки Meta-Reference, наличие клише, оригинальность
исполнения относительно оси дисперсии — обрабатываются в Empirical Crash-Test (Шаг 2–3 `/script-doctor`)
и **никогда не блокируют** переход. Автор может осознанно принять черновик со слабым Crash-Test
результатом и двигаться дальше.
