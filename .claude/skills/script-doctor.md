# /script-doctor — Doctoring Engine

Строгая 3-шаговая валидация черновика автора. Это не редактура и не дописывание — система не предлагает
готовых формулировок текста, она диагностирует и задаёт вопросы.

**Обязательно к прочтению перед выполнением:** [`CLAUDE.md`](../../CLAUDE.md) целиком. В частности:
роster модулей не зашит заранее (§1), развилки модулей не разрешаются системой (§2), Crash-Test не
блокирует и не наказывает за неклишированность (§3), блокирует только `core/pipeline_config.md` по
правилу A+D (§4).

## Шаг 0: Приём черновика, определение roster'а и проверка гейта

1. Прочитать список файлов в `training/books/` — это полный текущий набор модулей. Ничего сверх
   реально зарегистрированного не подразумевается (см. `CLAUDE.md §1`). Если модулей меньше двух —
   предупредить пользователя: полноценных дебатов не будет, только разбор в рамках того, что есть
   (один модуль — один голос без спора; ноль — только структурный разбор без Theoretical Layer).
2. Разобрать черновик по [`core/parsing_matrix.md`](../../core/parsing_matrix.md) — Base Layer,
   Beat Layer, все зарегистрированные модули Module Layer, независимо друг от друга (как в
   `/script-learn`, но без Meta-Reference разметки на этом шаге).
3. Определить текущую стадию pipeline (Logline / Character / Treatment) по тому, какие поля вообще
   заполнены в черновике.
4. Прогнать [`core/pipeline_config.md`](../../core/pipeline_config.md) для этой стадии: только
   проверка (A) пустых обязательных полей (универсальных + `required: true` у зарегистрированных
   модулей) и (D) жёсткого чек-листа структурного отсутствия.

**Если гейт не пройден** — остановиться здесь. Сообщить автору конкретно, какое поле пусто или какой
структурный элемент отсутствует, и не запускать дебаты. Это единственное место во всём `/script-doctor`,
где допустима блокировка — дальше по шагам блокировки не будет, что бы ни показали дебаты или Crash-Test.

## Шаг 1: Theory — дебаты модулей, Unified Theoretical Variant

Каждый зарегистрированный модуль выносит независимый вердикт по каждому значимому `beat_id` черновика,
в своих терминах (см. `core/term_correspondence_map.md`, если нужно объяснить автору кажущееся сходство
формулировок двух модулей).

Там, где модули расходятся в диагнозе одного `beat_id` — зафиксировать `fork` (формат из
`parsing_matrix.md`). **Unified Theoretical Variant — это не единый вердикт.** Это полная структура:
согласованные пункты + явные, неразрешённые развилки. Не выбирать «более убедительный» модуль и не
усреднять — это запрещено (CLAUDE.md §2).

Для каждой развилки подготовить интерактивное поле `[ ]`, которое будет предложено автору в выводе.

## Шаг 2: Empirical Synthesis — сборка Meta-Reference

1. Проверить, есть ли вообще файлы в `training/screenplays/`. **Если пул полностью пуст** — Шаги 2 и 3
   пропускаются целиком. Сообщить об этом честно и явно (например: «Эмпирический пул пуст — Crash-Test
   пропущен, ничего пока не сопоставляю. Выполнен только Шаг 1 — теоретические дебаты»), не пытаться
   имитировать сравнение и не подставлять память о фильмах вместо реального `/script-learn` разбора.
   Это не блокировка pipeline (см. CLAUDE.md §4) — просто честное «нечего сравнивать», доктор продолжает
   работать без этого слоя.
2. Если пул не пуст — взять `genre_type` и `tropes` черновика и найти совпадающие эталонные сценарии в
   `training/screenplays/*.md` по их YAML frontmatter.
3. Отобрать релевантный пул (обычно ~10, может быть меньше, если пул жанра ещё мал — в этом случае
   явно предупредить автора, что Crash-Test менее надёжен из-за малой выборки).
4. Динамически синтезировать `META_REFERENCE` для этой сессии (в память, не обязательно на диск —
   см. «Персистентность» ниже) из `meta_reference` блоков отобранных сценариев:
   - собрать `function_tag` по совпадающим типам `beat_id`/структурной роли;
   - построить карту дисперсии (`variance_axis` → распределение `variance_position` по всем сценариям
     пула) — что инвариантно в жанре, что варьируется, а что редко встречается;
   - подтянуть `default_deviation` там, где он есть, как примеры удачных уклонений от жанрового дефолта.

Синтез компилирует жанровые константы и структурные рифмы **из функций и дисперсии, а не из списка
самых частых событий** (CLAUDE.md §3) — иначе Meta-Reference превращается в каталог клише вместо
эталона органичности.

### Персистентность Meta-Reference

По умолчанию `META_REFERENCE` — эфемерный артефакт сессии. Если автор явно просит сохранить его для
повторного использования, записать снимок в `training/screenplays/_meta_reference_cache/[genre_type].md`
с пометкой даты синтеза и состава пула (чтобы было понятно, что кеш устареет при добавлении новых
сценариев через `/script-learn`).

## Шаг 3: Crash-Test — сверка и поиск клише

Для каждого значимого `beat_id` черновика сравнить его `function_tag` (извлечённый по той же логике
function-over-form, что и в `/script-learn`) с картой дисперсии Meta-Reference для этой структурной роли.

**Флаг «плоский штамп» ставится, только если одновременно:**
1. исполнение черновика ложится на самую частую (`variance_position: common`) точку оси дисперсии, **и**
2. заявленная функция бита не выполняется для *конкретного* героя черновика (событие происходит, но
   ничего не меняет и никого не раскрывает — в терминах реально зарегистрированных модулей).

Если исполнение частое, но функция реально работает для этого героя — это не штамп, а корректное
использование жанровой константы, и помечать это как проблему запрещено.

Если в пуле есть задокументированные `default_deviation` для этой структурной роли — предложить их
автору как иллюстрацию альтернативного пути, не как готовое решение для копирования.

Результат Шага 3 — всегда рекомендация, никогда не блокировка (CLAUDE.md §4).

## Вывод: формат дебатов в терминале

Короткий, характерный диалог, не отчёт с ярлыками. Каждый зарегистрированный модуль говорит от лица
своей книги — не абстрактной «системы». Пример тона (не шаблон для копирования дословно — конкретные
голоса зависят от того, какие модули реально зарегистрированы, а не от примера ниже):

```
MODULE_A:  Причинная цепь до этой сцены держится — но откуда взялось решение героя в сцене 34?
           Ничего до этого его к нему не готовило.

MODULE_B:  Не соглашусь насчёт "ничего не готовило" — что-то важное для героя смещается ещё в сцене 20.

MODULE_C:  [FORK] Я вижу здесь незакрытый внутренний конфликт, заявленный в первом акте и просто...
           испарившийся.

  [ ] MODULE_C отмечает неразрешённый внутренний конфликт — считать это открытым вопросом истории
      или закрыть как сознательное решение?
```

Развилки выводятся как реплики с пометкой `[FORK]`, сразу с интерактивным полем `[ ]` под ними —
не отдельной таблицей после дебатов. Crash-Test результаты выводятся отдельным блоком после дебатов,
явно промаркированным как рекомендация, не как вердикт. Если зарегистрирован только один модуль —
формат остаётся тем же, но без реплик оппонентов и без `[FORK]`; система не выдумывает второй голос.
