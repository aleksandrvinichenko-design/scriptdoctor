# /book-learn — разбор теоретического первоисточника и регистрация модуля

Читает книгу теоретика сценарного мастерства, извлекает её собственные концепции и диагностические
вопросы и **регистрирует новый модуль**: записывает и дистиллированную базу знаний, и машиночитаемую
схему полей в `training/books/[module_key].md`. Это единственный способ, которым в системе появляется
модуль — до `/book-learn` его не существует, и никакой список модулей не зашит заранее ни в один
core-файл (см. [`CLAUDE.md §1`](../../CLAUDE.md)).

**Обязательно к прочтению перед выполнением:** `CLAUDE.md §1` и `§8`. Три жёстких правила оттуда:
(1) роster модулей не предполагается заранее — сколько книг добавлено, столько модулей и есть;
(2) дистилляция своими словами, не пересказ близко к тексту и не копирование;
(3) схема модуля выводится из книги с нуля, а не подгоняется под уже существующие поля.

## Аргументы команды

```
/book-learn [path_to_book] [module_key?]
```

`module_key` — короткий slug (обычно от фамилии автора: `howard`, `mckee`, `truby`, `snyder`, или
что угодно иное — это не закрытый список). Если не указан — предложить slug на основе имени автора
книги и подтвердить с пользователем перед записью.

Если `training/books/[module_key].md` уже существует — не перезаписывать молча. Спросить пользователя,
это (а) обновление того же издания, (б) новое издание той же книги, или (в) на самом деле другая книга
и нужен другой `module_key`.

## Шаги выполнения

### 1. Приём текста

Прочитать файл (PDF/TXT), получить целостный текст. Если есть оглавление — использовать его как
карту для последовательного прохода по концепциям автора, а не парсить книгу линейно кусками
произвольной длины.

### 2. Извлечение концепций и полей будущего модуля

Пройти по книге и выделить собственные, названные автором понятия — не общие слова о драматургии,
а термины, которые именно этот автор вводит или определяет по-своему (пример: не «конфликт» вообще,
а конкретно «moral argument» или «Save the Cat moment», если книга вводит именно такие термины).

Для каждого понятия, которое станет полем модуля, зафиксировать:
- точный авторский термин (на языке оригинала книги, не переводить сам термин);
- имя поля для машиночитаемой схемы (`snake_case`, образовано от термина);
- определение, пересказанное своими словами — что это, зачем это нужно в системе автора, чем
  отличается от смежных понятий внутри этой же книги;
- диагностический вопрос, который это понятие задаёт при применении к конкретному сюжетному биту
  (формулировка, пригодная для использования в дебатах `/script-doctor`);
- является ли поле, по логике самой книги, **обязательным** для минимально состоятельного анализа
  персонажа/структуры (`required: true`) или вспомогательным (`required: false`);
- к какой стадии пайплайна это поле в первую очередь относится: `logline | character | treatment`
  (используется гейтами `core/pipeline_config.md`).

Короткая цитата (не более одной-двух фраз) допустима только там, где формулировка автора настолько
точна, что пересказ теряет смысл — не как основной способ фиксации понятия.

Схема формируется **с нуля из содержания книги** — не ищи существующий шаблон полей, под который
нужно подогнать эту книгу. Если в проекте уже есть другие модули с похожими полями — это нормально,
совпадение не означает, что поля нужно унифицировать (см. `CLAUDE.md §1` — модули не сливаются).

### 3. Проверка пересечений с уже зарегистрированными модулями

Прочитать список существующих файлов в `training/books/` (кроме самого разбираемого). Если
обнаруживается явное пересечение нового понятия с термином уже существующего модуля — зафиксировать
как `Term Correspondence Proposal` с указанием типа (эквивалент / частичное пересечение / ложный друг)
и кратким обоснованием.

Не редактировать [`core/term_correspondence_map.md`](../../core/term_correspondence_map.md) напрямую —
этот файл читают во время живых дебатов, ошибочная запись там искажает объяснения автору, поэтому он
обновляется только после review пользователем.

Если `training/books/` пуст (это первая книга) — этот шаг пропускается, сравнивать не с чем.

### 4. Запись файла модуля

Путь: `training/books/[module_key].md`.

```yaml
---
author: <str>              # полное имя автора книги
book_title: <str>
module_key: <slug>
source_file: <str>         # путь к исходному файлу книги
learned_at: <ISO date>
---
```

Далее — машиночитаемая схема (используется `parsing_matrix.md` Module Layer и гейтами
`pipeline_config.md`):

```yaml
module_schema:
  <field_name>:
    required: <bool>
    applies_to: <"logline"|"character"|"treatment">
    type: <str>
```

Затем — по одной прозаической секции на понятие:

```markdown
## <Авторский термин>

**Поле:** `<module_key>.<field_name>`
**Определение:** <своими словами>
**Диагностический вопрос:** <вопрос для применения к биту в дебатах>
**Источник:** <глава/раздел книги, без объёмного цитирования>
```

В конце файла — блок, только если он непустой:

```markdown
## Term Correspondence Proposals
- <это понятие> vs <термин другого module_key>: <тип соответствия> — <обоснование>
```

### 5. Обновление зависимых модулей при повторном запуске

Если это переиздание уже существующего модуля и в новой версии книги появилось понятие, отсутствующее
в текущей `module_schema` — это `Schema Extension Proposal`: показать пользователю предлагаемое новое
поле и спросить, добавлять ли его в схему сейчас. Не применять молча — уже размеченные этим модулем
эталонные сценарии в `training/screenplays/` не будут иметь значения для нового поля, и это нужно
явно проговорить с пользователем (потребуется ли повторный `/script-learn` по существующему пулу).

## Вывод пользователю

Краткое резюме, не полный текст файла:
- зарегистрирован модуль `<module_key>`, сколько полей в его схеме, сколько из них `required`;
- сколько предложено добавлений в `term_correspondence_map.md` (если применимо);
- путь к записанному файлу;
- если это было расширение существующего модуля — что именно предложено добавить и ждёт решения.
